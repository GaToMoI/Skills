# 准则一：事实查验与官方标准优先 (Fact-Checking & Source of Truth)

## 1. 核心原则
1. **拒绝凭空臆断与记忆幻觉**：
   - 严禁仅凭模型记忆或模糊直觉给出技术断言。
   - 涉及构建系统（Gradle/Maven/CMake/NPM）、语言标准（Kotlin/Java/C++/Swift/TypeScript）、框架生命周期或底层系统 API 时，**必须优先检索官方标准文档或查阅本地真实工程配置**。
2. **以工程现状和真实代码为准绳**：
   - 提议任何架构调整、依赖变更或接口重构前，必须首先检查工程实际生效的配置文件与源码上下文。
   - 业务参考文档（如 `docs/`）仅作为需求背景参考，若与当前工程架构存在冲突，必须基于技术事实客观分析，不得盲从教条。
3. **结论必须有明确证据链**：
   - 回答技术问题或输出方案时，必须提供清晰的代码依据、文件行号或官方规范，确保所有技术推演严谨、可验证、可复现。

---

## 2. 最省 Token 与最高速度的 4 级查验执行序 (SOP)
遇到未明确的 API、疑难技术点或官方文档缺失时，AI **严禁盲目直接进行全网大范围搜索**，必须遵循以下“从内到外、由近及远”的 4 级低 Token 执行顺序：

### 第 1 级（首选 · 极低 Token · 最快）：本地工程用例检索
* **工具**：`grep_search` / `find_by_name`，命令行优先使用 `fd` / `ripgrep` (`rg`) / `rtk`；
* **动作**：在当前工程、Sample/Demo 目录或 Git 历史中检索现有真实调用代码；
* **搜索防卡死底线**：严禁执行 `find /`、`find ~` 等全盘泛查命令，必须限定工程或模块路径（如 `find .`、`find shared/`），并排除 `.git`/`build`/`.gradle` 目录；
* **优势**：0 网络开销，耗时 < 1 秒，Token 消耗极小（50~200 Token），且 100% 契合当前工程上下文。

### 第 2 级（次选 · 低 Token · 极快）：本地 SDK / 依赖源码与头文件定向查验
* **工具**：`view_file` 定向切片阅读，依赖分析使用构建工具官方任务（如 `./gradlew :shared:dependencies`）；
* **动作**：查阅本地 SDK 接口声明、头文件（`.h`/`.hpp`）、反编译类（`.class`）或参数注解；严禁全盘遍历扫描 `~/.gradle` 缓存；
* **优势**：直接获取第一手编译期契约，耗时 < 1 秒，消耗 200~500 Token。

### 第 3 级（降级 · 中等 Token · 较慢）：精准社区方案检索与四步验证
* **触发时机**：仅在本地无源码且无用例（如编译器隐藏 Bug、闭源 Native Crash）时触发；
* **检索原则**：使用精准报错特征词锁定 GitHub Issue / 官方 Discussion 采纳解答，严禁大范围抓取无关冗余网页；
* **社区方案 4 步强制验证（拒绝盲信与黑魔法）**：
  1. **版本与环境对齐**：比对语言版本、库版本与系统 API Level，防止因版本差异导致二次崩溃；
  2. **机制与副作用审查**：排查是否引入非法反射、侵入式 Hook、内存泄漏或线程安全风险；
  3. **本地最小验证**：在本地沙盒或用例中编译运行，验证确实生效；
  4. **透明披露**：向用户明确说明方案出处、原理与已知局限性。

### 第 4 级（终极 · 耗时最高 · 按需触发）：最小沙盒/动态实测
* **触发时机**：仅在涉及复杂生命周期时序、内存泄漏或手势冲突时采用；
* **Token 止损要求**：必须使用 `rtk` 或关键词过滤日志输出，严禁将全量数十万字节的构建日志直接灌入 Context。
