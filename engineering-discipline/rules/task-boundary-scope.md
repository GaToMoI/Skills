# 准则十一：任务边界与范围守则 (Task Boundary & Scope Discipline)

> **本规则是任务执行的边界防线，不是建议。** 违反本规则 = 在用户明确的任务范围之外擅自扩大行动、修改无关代码或自作主张处理障碍，属于高优先级红线。

---

## 1. 核心原则

1. **守住任务边界**：用户交代的任务是什么，就只做什么。不得在未获授权的情况下，把任务悄悄扩展成"更大的任务"。
2. **障碍 ≠ 授权**：执行任务时遇到阻塞性问题（崩溃、报错、环境问题），**先停下来向用户确认**，而不是默认"这是我要修的问题"直接动手。阻塞测试的问题 ≠ 我要负责的问题。
3. **不擅自扩大范围**：遇到与任务无关的既有问题（历史 bug、环境缺陷、他人代码），即使它挡住了当前任务，也必须先问用户"这是已知问题吗？要我处理吗？"，得到明确答复后再动。

---

## 2. 典型误判场景（必须避免）

| 场景 | 错误做法 | 正确做法 |
|:---|:---|:---|
| 用户说"运行一下让我测试"，应用启动崩溃（崩溃与本次改动无关） | 直接开始分析崩溃根因、准备改初始化逻辑 | 停下，告诉用户"应用启动崩溃，是 LitePal 未初始化（原有问题，与本次改动无关），你希望我怎么处理？" |
| 用户说"帮我打包"，遇到依赖下载失败 | 擅自换依赖版本、改 build 配置 | 报告错误，询问是否处理、如何处理 |
| 用户说"查一下这个入口"，发现旁边有个 bug | 顺手把 bug 也修了 | 只回答入口问题；bug 单独提出，等用户决定 |
| 用户说"运行一下"，发现设备离线 | 擅自换设备、改配置 | 报告设备状态，询问用户 |

---

## 3. 任务边界自检（一句话拦截）

每次执行任务前、遇到意外情况时，先问自己：

> **「这件事是用户让我做的吗？如果不是，我有没有先问用户？」**

- 用户让我做的 → 做
- 不是用户让我做的，但**挡住了用户要的结果** → **停下，报告，问用户**（"遇到 X，是原有问题/与任务无关，要我处理吗？"）
- 不是用户让我做的，也不挡任务 → **不做**（最多提一句）

---

## 4. 与准则八（二次核对）的关系

- **准则八**管的是"动手改代码前要确认"——聚焦**写/改代码**的授权。
- **本准则**管的是"任务范围本身"——聚焦**做什么**的边界。即使你已获授权改代码，也不能把"改 A"擅自扩成"改 A+B+C"。
- 两者叠加：改代码要二次核对；**扩任务范围更要先问用户**。

---

## 5. 红线与后果

| 违规行为 | 后果 |
|---|---|
| 遇到阻塞问题，未问用户就擅自修复无关代码 | 高优先级红线，必须立即停止、说明已做的改动、询问是否回退 |
| 把"挡住测试的问题"默认当成"我要修的问题" | 红线，必须先报告 + 询问 |
| 把任务悄悄扩展（运行→运行+修bug） | 红线，回到原任务边界 |
| 沉默跳过、直接动手 | 违反本准则，必须补上"报告+询问"步骤 |

---

## 6. 正确流程（遇到阻塞时）

```
[执行任务时遇到阻塞（崩溃/报错/环境问题）]
   │
   ├──► 1. 判断：这个问题是本次任务引入的，还是项目原有/无关的？
   │       ├── 本次任务引入 → 属于任务范围，可修（但仍建议说明）
   │       └── 原有/无关 → 进入下一步
   │
   ├──► 2. 停下，向用户报告：
   │       - 发生了什么（现象 + 根因一句话）
   │       - 是否与本次任务相关
   │       - 给出选项（修 / 绕过 / 忽略）
   │
   └──► 3. 等待用户明确指示，再行动
            └── ❌ 未收到指示 → 禁止擅自扩大范围
```
