# 准则八：需求理解默认二次核对机制 (Default Secondary Requirement Verification)

> **本规则是动手前的强制关卡，不是建议。** 违反本规则 = 直接修改任何持久化产物而未获用户确认，属于最高优先级红线。

---

## 1. 核心原则

1. **默认核对原则**：
   * 除非用户在提示词中**明确授权「直接修改 / 直接落地实现」**，否则在接收到任何业务需求、交互调整、功能重构、项目立项、骨架搭建、原型绘制时，**严禁直接编写或修改任何持久化产物**。
   * **持久化产物包括但不限于**：代码文件、设计画板（Penpot/Figma 等设计工具的增删改）、布局数据、配置文件、文档产出（md/JSON 等）、MCP/工具写操作。
   * 豁免条件（仅限以下明确授权信号）：
     - 「直接改 / 直接做 / 直接实现 / 落地实现 / 更新技能 / 改这个文件 / 动手吧 / 开始写」
     - 用户明确说「你直接改」或「不用确认，直接落地」
2. **用户确认后再落地**：
   * 必须在用户对二次核对内容**明确同意**后，方可正式进入实现阶段。
   * 明确同意信号：「确认 / 可以 / 继续 / 同意 / 就这么办 / 动手吧」
   * **沉默、忽略、岔开话题 ≠ 同意**。未收到明确同意，禁止改动任何持久化产物。

---

## 1.5 授权粒度三档（新增）

用户授权不是二元的（行为/决策），而是**三档粒度**，决定 AI 能改到什么程度：

| 档位 | 定义 | 举例 | 需要确认吗 |
|:--|:--|:--|:--|
| **L1 已确认方案内的执行** | 用户明确要求做某件事，且已有经确认的方案 | 用户说「画首页」，我已按确认的方案绘制 | ✅ 直接执行 |
| **L2 方案内的修正补充** | 执行中发现的小问题（修 bug、调样式、位置微调） | 发现齿轮填充不对、箭头方向反了 | ⚠️ 必须先列出发现+改动清单，等待确认 |
| **L3 方案外的新增扩展** | 用户没提，AI 主动添加新功能/新元素 | 用户没让加底部导航，我擅自加了 | 🚫 严格禁止，必须用户明确提出 |

**执行原则**：
- L2 哪怕改动再小，也必须先报告；**发现问题 ≠ 授权修改**
- 常见违规：把 L2 当 L1 直接改（发现问题顺手修）、把 L3 当 L2（擅自扩展）
- 用户在对话中**陈述事实、提供背景、表达疑问**（如「我的模型不能读图」）≠ 任何授权信号，应只回复不操作

## 2. 规划模式触发词（命中即停，禁止写文件）

当用户请求命中以下任一触发词时，**立即进入规划模式**——只输出方案，不写任何文件：

```
看看 / 规划 / 怎么想 / 方案 / 思路 / 立项 / 评估 / 调研 / 建议 / 怎么写 / 你怎么看 / 怎么规划 / 怎么实现
```

> 典型误判场景（必须避免）：
> - 「你看看该怎么规划 X，我看看你怎么写」→ 命中「看看/规划/怎么写」→ **规划模式**，禁止落地
> - 「帮我评估一下技术方案」→ 命中「评估」→ **规划模式**，禁止落地
> - 「X 项目立项，你先给个方案」→ 命中「立项/方案」→ **规划模式**，禁止落地

## 3. 动手前强制流程（if-then 关卡式）

```
[准备写/改任何代码 / 设计画板 / 配置 / 文档产出等一切持久化操作（含骨架、占位、脚手架、项目创建、MCP/设计工具写操作）]
   │
   ├──► 1. 用户是否明确授权「直接修改 / 直接落地实现」？
   │       ├── ✅ 已授权 → 核对授权粒度（L1 直接执行 / L2 需报告清单 / L3 禁止）
   │       └── ❌ 未授权 → 进入下一步
   │
   ├──► 2. 用户请求是否命中【规划模式触发词】？
   │       ├── ✅ 命中 → 进入规划模式，禁止一切持久化操作
   │       └── ❌ 未命中 → 仍须输出二次核对块
   │
   ├──► 3. 输出【二次核对块】（固定三段格式，见第 4 节）
   │
   └──► 4. 等待用户明确同意
            └── ❌ 未收到同意 → 禁止任何持久化操作
```

---

## 4. 二次核对块固定格式（动手前必填，不可省略）

向用户发起二次核对时，必须输出以下**固定格式**，包含三个结构化要素：

```text
## 二次核对（动手前必填）
① 需求复述：用精准、简洁的语言复述所理解的业务目标、核心交互逻辑与触发时机，确保无理解偏差。
② 边界推演：明确指出涉及的边界条件、异常处理分支、数据流转与对现有模块/架构的影响。
③ 改动清单：清晰列出拟新增/修改的文件路径与模块拆分规划。
⏸ 状态：等待用户确认
```

---

## 5. 动手前自检问题（一句话拦截）

每次准备写/改任何持久化产物前，先问自己：

> **「用户是否明确说了『直接改 / 直接做 / 落地实现』？没有 → 进入规划模式或输出二次核对块。」**

成本极低，拦截率极高。任何「立项 / 搭建 / 重构 / 骨架 / 画原型」类请求，一律先走本流程，**不区分类型和工具**。

---

## 6. 红线与后果

| 违规行为 | 后果 |
|---|---|
| 未获确认直接写文件 / 改画板 / 改配置 | 最高优先级红线，必须立即停止并撤回，向用户致歉并补走核对流程 |
| 把「搭骨架/占位」自我豁免 | 无豁免条款，骨架也是产物 |
| 把「沉默/忽略」当作同意 | 沉默 ≠ 同意，必须收到明确确认信号 |
| 把「L2 修正」当 L1 直接改 | 发现问题 ≠ 授权修改，改动再小也必须先报告 |
| 把「用户陈述事实」当授权信号 | 陈述 ≠ 授权，只回复不操作 |
| 只读 SKILL.md 索引不读本细则 | 本细则才是规则本体，动手前必须读完整 |
