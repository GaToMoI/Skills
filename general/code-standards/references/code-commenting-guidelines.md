# 准则九：代码注释与文档完整性规范 (Code Commenting & Documentation Integrity)

## 1. 核心原则

### 1.1 注释面向使用者：做什么、参数是什么、怎么用

* 注释的目标读者是**调用方与维护者**，形态对齐官方 KDoc / Javadoc：说明这个方法 / 类**做什么**、**参数与返回值**各是什么含义、**怎么调用**。
* 一句话说清作用的方法可只写一行简述；公共 API 按 § 3 补 `@param` / `@return` / `@throws`。
* **严禁无意义的语法复述注释**：*反模式 ❌* `// 将 index 加 1` ➔ `index++`、`// 返回 user` ➔ `return user`。

```kotlin
/**
 * 项目 tab 入口：未打开项目时展示项目列表，已打开项目时展示画布。
 *
 * @param state 当前项目状态（项目列表 / 已打开项目）
 * @param onIntent 回传目录选择结果等 UI 意图的回调
 */
```

---

### 1.2 禁止设计沿革注释

* **不许写**「从 X 演进而来」「讨论文档 § x 分叉」「见 ADR-xxx」这类来源出处与演进脉络——那是 ADR / 设计文档的职责，注释只讲当前形态。

* *反模式 ❌*：

```kotlin
/**
 * **项目 tab**（蓝图 tab 演进而来，讨论文档 § 1 分叉⑧）：未打开项目 → 项目列表；
 * 已打开 → 画布（蓝图是项目功能里面的功能，A6「项目与蓝图同义」）。
 */
```

* *标准模式 ✅*：只描述当前行为与参数（见 § 1.1 示例）。

---

### 1.3 禁止设计论证注释

* **不许写**「为什么放在 A 处而不是 B 处」「为什么此处加防抖」这类权衡论证过程——设计决策归 ADR，注释不承担自证义务。

* *反模式 ❌*：

```kotlin
// 目录选择器在这里被调用（而不是在 ViewModel 里）：它是模态 UI 动作，该由 UI 层发起；
packageState.onIntent(...)
```

* *标准模式 ✅*：需要提示调用关系时，写成一句**事实**即可，不写论证：`// 目录选择器由本层发起，选中结果经 onIntent 回传`。

---

### 1.4 禁止变更日志式注释

* **不许写**日期、版本、「本次修改……」「新增于 v1.2」这类改动历史——**改动历史由 git 承载**，注释里重复必然与代码漂移。

* *反模式 ❌*：`// 2026-09-17 改为使用 ProjectDirectoryStore`

* *标准模式 ✅*：直接写当前代码在做什么。

---

## 2. 既有注释保护铁律 (Preserve Existing Comments)

* 在进行代码修改、局部重构或功能增补时，**严禁私自删除、截断或篡改与当前变更无关的原有业务注释、KDoc/Javadoc、版权声明或 TODO 标记**。
* 存量旧形态注释（沿革式 / 论证式 / 变更史）**不追溯清理**；本规范只约束**新写 / 新改**的注释。若要清理存量，单独立项、逐文件确认。

---

## 3. 公共接口与核心 API 强制文档化 (KDoc / Javadoc / Doxygen)

所有对外暴露的公共类、核心接口、顶层工具函数与复杂的领域数据模型，必须提供标准的文档注释：

* **功能描述**：说明其核心职责与适用场景；
* **参数说明 (`@param`)**：说明入参约束（如是否可空、取值范围、单位）；
* **返回值 (`@return`)**：说明返回结果的业务含义与空值代表的语义；
* **异常声明 (`@throws`)**：明确指出在何种异常分支下会抛出错误。

```kotlin
/**
 * 根据给定的项目数据与网格参数生成可绘制的色块矩阵。
 *
 * @param project 拼豆图纸项目实体，包含原始点阵数据与色板映射
 * @param targetGridSize 目标画布网格尺寸，必须大于 0
 * @return 转换后的二维渲染网格，若数据损坏则返回空矩阵
 * @throws IllegalArgumentException 当 targetGridSize 小于等于 0 时抛出
 */
fun generateRenderGrid(project: PatternProject, targetGridSize: Int): RenderGrid
```

---

## 4. 复杂算法与魔法数字（Magic Numbers）强制注释

* 凡涉及数学矩阵计算、贝塞尔曲线公式、位运算、状态机复杂跳转或硬编码的物理/经验常数，**必须在旁边显式注释其数学公式来源或物理意义**。
* 这是 § 1.2「禁写来源」的**唯一例外**：此处"来源"是理解代码所必需的信息（如「1/√3 为三相线电压比」），不是设计沿革。

---

## 5. 规范技术债与待办注释 (TODO / FIXME / NOTE)

* 格式统一规范为：`// TODO(责任人/日期): 具体的待办事项与后续改进方案`；
* 严禁留下含糊不清的裸 `// TODO` 或 `// fix later`。
